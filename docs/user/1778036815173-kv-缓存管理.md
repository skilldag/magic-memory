KV_CACHE(7)                Transformer 推理优化核心            KV_CACHE(7)

NAME
       kv_cache — 键值缓存，自回归生成中避免重复计算的动态内存机制

SYNOPSIS
       #include <kv_cache.h>

       typedef struct {
           Tensor *K;          /* 缓存的键张量，形状 [B, h, T_prev, d_k] */
           Tensor *V;          /* 缓存的值张量，形状 [B, h, T_prev, d_v] */
           int     T_prev;     /* 已缓存的序列长度 */
       } KVCache;

       /* 推理一步 */
       K_new, V_new = linear_proj(x_new);              /* 仅计算新 token */
       K = concat(cache->K, K_new, dim=time_axis);     /* 追加到缓存 */
       V = concat(cache->V, V_new, dim=time_axis);
       cache->T_prev += 1;

       context = attention(Q_new, K, V);               /* Q_new 仅与完整 K,V 交互 */

DESCRIPTION
       在 Transformer 解码器的自回归推理中，每个新 token 的生成
       都需要关注所有历史 token。朴素实现每步重算全部 K,V 会导致
       计算量与序列长度平方成正比，KV 缓存通过存储并复用历史键值
       彻底解决了这一效率瓶颈。以下通过“问题—概念—推导—新问题”
       链条展开其核心原理。

问题 1: 自回归推理每步生成一个新 token，若每步都对完整序列重新执行
        自注意力，计算量如何演化？为何不可接受？
       │
       ├── 计算分析 (无缓存时一步推理)
       │   │
       │   │   假设已生成 T 个 token，现要生成第 T+1 个。
       │   │   需将长度为 T+1 的完整序列馈入解码器，计算自注意力：
       │   │       Q,K,V ∈ ℝ^( (T+1) × d )
       │   │       Score = Q·Kᵀ  → 复杂度 O((T+1)²·d)
       │   │       Context = softmax(...)·V → O((T+1)²·d)
       │   │   随 T 增长，每步计算量平方攀升，生成长序列时极慢。
       │   │
       │   └── 根因：每次生成都重新为相同的历史 token 计算 K,V，
       │           而这些历史表示在迭代间 完全不变。
       │
       └── 解决概念: KV 缓存 (Key-Value Cache)
           │
           │   维护两个张量 cache_K, cache_V，存储所有历史 token 的
           │   键和值向量。新 token 到来时，仅计算新 token 的 Q,K,V，
           │   然后将新 K,V 追加进缓存。注意力计算时，Q_new 与缓存的
           │   全部 K,V 做点积，从而复用之前的结果。
           │
           │   ▸ 计算对比 (第 T+1 步):
           │       无缓存: O((T+1)²·d)
           │       有缓存: O((T+1)·d)   (新 Q 仅与 T 个历史 K 点积)
           │       生成全部 T 个 token 的总复杂度从 O(T³) 降至 O(T²)。
           │       每次新增 token 成本与 T 成线性，而非平方。
           │
           │   ▸ 命名:
           │       Key(键) 和 Value(值) 被存储下来供后续查询反复取用，
           │       仿若计算机体系结构中的高速缓存，故称 KV Cache。
           │       也称 Past-Key-Value 或 Decoder Cache。
           │
           │   ▸ 直观例子:
           │       生成“我 爱 猫”后要预测下一个词。缓存里已有 K,V 为：
           │         K[0..2], V[0..2] 分别对应“<s> 我 爱”。
           │       预测“猫”时，新 token 的 Q(“爱”) 只需点这三个 K，
           │       无需重新计算“<s>”和“我”的 K,V。生成完“猫”后，
           │       再将其 K,V 追加入缓存，供下一步使用。
           │
           └── 引出的新问题:
              缓存随序列增长而线性膨胀，显存占用和批处理管理成为新挑战。

问题 2: 缓存如何组织与分配？不同 batch 句子长度不等怎么办？
       │
       ├── 子概念: 缓存的结构与预分配
       │   │
       │   │   缓存通常为 [B, h, T_max, d_k] 的张量，其中：
       │   │       B  = batch size
       │   │       h  = 多头数
       │   │       T_max = 最大生成长度（预分配或动态扩展）
       │   │   ▸ 预分配策略:
       │   │       推理前按最大生成 token 数分配连续显存，避免反复
       │   │       开辟、拷贝的开销。生成过程中逐步填充。
       │   │   ▸ 动态增长:
       │   │       对于变长生成（如 early stopping），可使用动态扩容，
       │   │       但需处理内存碎片与设备同步开销。
       │   │
       │   └── 批处理长度不等问题:
       │       同一 batch 内句子结束时间不同。已结束的句子不必继续
       │       生成，但仍需维护其缓存以避免索引错乱。两种主流方案：
       │       · 左填充 (Left-padding): 将较短序列在左侧填充 pad token。
       │         此时有效上下文靠右对齐，生成从右侧追加，缓存索引连续。
       │       · 条状掩码 (Ragged batch/Continuous batching):
       │         动态拼接有效 token，通过 custom mask 区分序列边界，
       │         极大提升 GPU 利用率（常用于生产推理引擎如 vLLM）。
       │
       └── 引出的新问题:
           长序列、多轮对话等场景，缓存体积可能超出 GPU 内存。
           如何压缩或淘汰缓存？

问题 3: 如何降低 KV 缓存的内存占用？
       │
       ├── 解决概念: 多头缓存削减
       │   │
       │   │   原始多头注意力为每个头独立存储 K,V，可优化为：
       │   │   · 多查询注意力 (MQA): 所有查询头共享同一组 K,V。
       │   │       缓存形状从 [h, T, d_k] 降至 [1, T, d_k]，
       │   │       压缩比为 h。通常性能略有下降但推理加速显著。
       │   │   · 分组查询注意力 (GQA): 将 h 个头分成 g 组，
       │   │       每组内共享 K,V，压缩比为 h/g。
       │   │       LLaMA 2/3 等模型广泛采用。
       │   │
       │   └── 效果: 缓存大小 ∝ (num_kv_heads) · T · d_k，
       │            减少 kv 头数直接线性降低内存。
       │
       ├── 解决概念: 滑动窗口缓存
       │   │
       │   │   仅保留最近 W 个 token 的 K,V，丢弃更早的历史。
       │   │   ▸ 公式:
       │   │       K_win = K_cache[T-W : T]
       │   │       V_win = V_cache[T-W : T]
       │   │   适用于语言模型本地依赖较强的特性（如 Mistral）。
       │   │   可结合全局 token（如 BOS）保留进一步缓解遗忘。
       │   │
       │   └── 局限: 完全丢弃长程信息可能损害长文任务。
       │
       ├── 解决概念: 量化缓存 (KV8/FP8/KV4)
       │   │
       │   │   以半精度 (FP16) 或 8bit 甚至 4bit 存储 K,V，
       │   │   使用时反量化回计算精度。内存压缩 2~4 倍。
       │   │
       │   └── 权衡: 精度损失可能影响生成质量，需校准。
       │
       └── 解决概念: 卸载到 CPU 或 NVMe (Offloading)
           将早期缓存的 K,V 转移到 CPU 内存或硬盘，当前窗口保留在 GPU。
           按需预取，兼顾长上下文与显存限制。

缓存交互全流程 (树状总结)
       第 t 步推理:
       │
       ├─ 1. 输入 x_t (新 token 嵌入) → Linear 投影得 q_t, k_t, v_t
       │
       ├─ 2. 检查缓存: 取 cache_K (T_prev 个历史键), cache_V (T_prev 个历史值)
       │
       ├─ 3. 拼接:
       │       K = concat(cache_K, k_t)   # 形状 [B, h, T_prev+1, d_k]
       │       V = concat(cache_V, v_t)
       │
       ├─ 4. 注意力: context = Attention(q_t, K, V)   # Q 只有 1 个 token
       │       (注意：q_t 维度 [B, h, 1, d_k]，不打掩码，自然只看见历史)
       │
       ├─ 5. 更新缓存: cache_K ← K, cache_V ← V, T_prev += 1
       │
       └─ 6. 后续层和输出投影，产生下一个 token 概率。

注意: 训练时的上三角掩码被缓存机制取代。推理中因为 Q 永远仅来自
       最新 token，它与过去所有 K,V 交互自然符合因果约束，无需显式掩码。

命名与记忆
       · KVCache / Past-Key-Value — 存储“已经被查询过的键值”，供未来复用。
       · 连续批处理 (Continuous batching) — 动态插入、移除序列来最大化吞吐。
       · MQA / GQA — 牺牲部分表达力换取缓存显著缩减。
