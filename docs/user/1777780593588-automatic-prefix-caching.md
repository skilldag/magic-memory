AUTOMATIC-PREFIX-CACHING(7)  推理内存优化            AUTOMATIC-PREFIX-CACHING(7)

名称
       automatic-prefix-caching — 基于内容哈希自动共享相同前缀的 KV 缓存块，
                                   消除重复存储与计算

概述
       Automatic Prefix Caching (APC) 利用分页 KV 缓存的块粒度和引用计数，
       通过 token 序列的哈希值识别逻辑等价的前缀，自动在多个请求间复用
       物理页。它使系统提示、少样本示例等高频前缀的 prefill 计算降至接近
       零成本，同时释放显存以服务更多并发请求。

描述
       本手册以问题链方式展开 APC 的设计动机、哈希匹配机制、写时复制
       隔离、以及和分页管理的协作。

       问题 0 · 共享前缀为何导致显存与计算双重浪费？
       │
       ├── 典型场景：多个请求共享相同的系统提示（如“你是一个有用的
       │   助手”）或对话历史前缀。长度为 L_share token。
       │
       ├── 无缓存的后果：
       │   - 每条请求独立分配 KV 块，存储完全相同的 K/V 张量。
       │     存储冗余：N 条请求浪费 (N-1)×L_share 的显存。
       │   - 每条请求的 prefill 均重复计算前缀的注意力，计算冗余：
       │       额外计算量 ≈ N × (L_share)² d。
       │   - 尤其当 L_share 很大（如长文档、代码库）时，浪费严重。
       │
       ├── 度量：共享率越高，浪费比越大。
       │       假设 batch 内共享比例为 r，则存储与计算的有效利用率仅为
       │       1 - r(N-1)/N ，理想情况下趋近于 1/N。
       │
       └── 核心需求：系统必须自动检测出“同一段 token 序列”，并使背后
           映射到同一块物理 KV 缓存，无需用户显式标注。

       问题 1 · 如何自动识别并共享相同的前缀块？
       │
       ├── 子概念：基于 token 序列的内容寻址
       │   - 将每个逻辑 KV 块（固定 B 个 token）关联一个内容标识。
       │   - 哈希函数 H：取该块对应的 token ID 序列 [t_0,...,t_{B-1}]，
       │     计算 64 位或 128 位哈希：
       │         hash = hash_func( token_ids[logical_block_start : +B] )
       │   - 维护全局哈希表： hash → 一组物理块指针（仅记录完整填满的块）。
       │
       ├── 共享匹配流程（prefill 时）：
       │       对于每个新请求的 prefill，逐逻辑块处理：
       │           hash = H(当前逻辑块的 token 序列)
       │           if hash in hash_table:
       │               从候选物理块中选取一个（通常唯一），进行精确
       │               token 比对验证，防止哈希碰撞。
       │               验证成功后，增加该物理块的引用计数。
       │               当前请求的 block_table 记录该物理页 ID。
       │               此逻辑块的 prefill 计算跳过（注意力直接读取该块）。
       │           else:
       │               分配新物理页，执行 prefill 计算写入 K/V。
       │               将该物理块插入哈希表（hash → physical_id）。
       │               引用计数设为 1。
       │
       ├── 节省的计算量（单条请求）：
       │       若命中 h 个块（每个块 B token），则跳过近似
       │           compute_saved ≈ h × (B² d)  的注意力计算。
       │       在长前缀场景，h 可达数百，加速显著。
       │
       └── 问题：多个请求共享某个物理块后，如果其中一个请求继续生成
           并修改了该块的内容（例如填充未满的块），则会导致其他请求
           读取到错误数据。如何防止？

       问题 2 · 共享前缀发生分叉时如何保证数据隔离？
       │
       ├── 分叉原因：前缀长度未必是块大小 B 的整数倍。
       │   - 假设共享前缀长度 L_share = kB + r，0 < r < B。
       │     最后一个逻辑块（第 k 块）仅包含 r 个 token，未满。
       │   - 多个请求共享该未满块。当某个请求继续生成第 (L_share+1)
       │     个 token 时，它可能进入同一个逻辑块，写入该块的第 r+1
       │     个位置的 K/V，这会覆盖或扩展该物理块的内容。
       │
       ├── 子概念：写时复制（Copy‑on‑Write）
       │   - 当需要对一个引用计数 > 1 的物理块进行写入时：
       │         1. 分配一个新的物理页。
       │         2. 将原物理页的全部已有 K/V 数据拷贝到新页。
       │         3. 原物理页的引用计数减一。
       │         4. 当前序列的 block_table 更新为新物理页 ID，
       │            新页的引用计数设为 1。
       │         5. 原物理页若引用计数归零，可留作下次分配或从
       │            哈希表移除；若仍被其他序列引用，保持不变。
       │   - 写入操作现在对新页进行，不影响其他共享者。
       │
       ├── 写时复制的触发点：
       │   · 序列追加 token 至未满块。
       │   · 某些推测解码或回滚场景需要回退到某历史块并进行修改。
       │
       └── 隔离代价：一次块拷贝（B 头维度的张量） + 一次 GPU 显存分配。
           因写时复制仅发生在块未满且被共享的少数边界情况，开销甚微。

       问题 3 · 如何维护哈希表并保证查找效率？
       │
       ├── 哈希表生命周期：
       │   - 插入：每当一个新物理块被完整填满（含 B 个 token）时，
       │     计算其哈希值并插入全局表。
       │   - 删除：当物理块引用计数降为 0 且块被回收时，从哈希表
       │     中移除对应条目。
       │   - 未满块不插入哈希表（因内容可被续写，不可作为稳定前缀）。
       │
       ├── 哈希碰撞处理：
       │   - 概率极低（64 位哈希对百万块级规模碰撞风险 < 10^-7）。
       │   - 为绝对安全，在命中哈希后需进行轻量的 token ID 确切比较。
       │     若比较失败则视为未命中，分配新块。
       │
       ├── 查找效率：
       │   - 哈希查找 O(1)，与缓存块总数无关。
       │   - 哈希键采用 token 序列，避免了逐元素比较的线性扫描。
       │
       └── 与 PagedAttention 的无缝粘合：
           哈希表与 block_manager 共享引用计数，prefill 与 decode 阶段
           均通过统一的 block_table 访问物理块，APC 对上层透明。

       问题 4 · APM 对整体性能的量化影响
       │
       ├── 首 token 延迟 (TTFT)：
       │        TP_apc ≈ T_chunk_hit × h  + T_chunk_miss × (total_blocks - h)
       │        当命中率高时，近似仅为未命中块的 prefill 时间。
       │        极端情况（100% 命中）：TTFT 降至仅输出嵌入与投影的时间，
       │        几乎为纯 decode 步级延迟。
       │
       ├── 吞吐量提升：
       │   - 省下的显存可用于扩大 batch 规模，吞吐量近似线性增加。
       │   - 尤其对于批量处理相同 prompt 的任务（如评估、代码补全），
       │     吞吐可提升数倍。
       │
       └── 适用边界：
           对无公共前缀的全随机请求无效果，但几乎不增加开销。
           对多轮对话、Chain-of-Thought 等场景收益巨大。

结论
        Automatic Prefix Caching 通过内容寻址将 KV 缓存提升为不可知
        的共享资源，消除了人工标注前缀的负担，并与分页管理、写时复制
        无缝结合。它是 vLLM 在保持高通用性的同时实现极致内存效率的
        关键拼图，使 LLM 服务在重复前缀负载下近乎“零成本”扩建上下文。
