SEQUENCE-PREEMPTION(7)        推理内存管理            SEQUENCE-PREEMPTION(7)

名称
       sequence-preemption — 在显存耗尽时主动驱逐低优先级序列的 KV 缓存
                             以接纳新请求，随后可恢复或重算的弹性机制

概述
       序列抢占与换出是 LLM 推理引擎应对过载的最后防线。当空闲物理页
       不足且新请求无法等待时，调度器依策略选择 Victim 序列，将其 KV 页
       打包转移至主机内存或直接丢弃，并在资源宽裕时通过重新加载或重计算
       换入恢复，从而在有限显存下实现超订服务并保障关键请求的延迟。

描述
       本手册沿问题推导链解释为何必须抢占、如何选目标、换出/换入的
       技术细节以及与分页管理的协同。

       问题 0 · 为何有分页管理仍会耗尽显存？
       │
       ├── PagedAttention 近乎消灭外部碎片，但物理页总量 M_phy 固定。
       │   动态到达的长 prompt 或大量并发请求可能使活跃页数逼近 M_phy。
       │
       ├── 若新请求所需页数 + 当前占用 > M_phy，且新请求优先级高或
       │   必须立即服务（如实时对话），系统只有两个选择：
       │       (a) 拒绝新请求，导致服务质量下降；
       │       (b) 从现有序列中回收页，即抢占。
       │
       ├── 显存容量约束：
       │        Σ 活跃序列的物理页使用量 ≤ 空闲池 + 已分配总量
       │   当左式接近甚至超过右式时，诞生抢占需求。
       │
       └── 引出问题：如何在不严重损害公平和整体吞吐的前提下选择
           牺牲序列？

       问题 1 · 如何选择 Victim 序列？
       │
       ├── 子概念：优先级驱动的抢占策略
       │   - 每个请求携带优先级标签（如由服务等级协议 SLA 决定）。
       │   - 候选集：所有可被换出的序列（未被锁定，如正在 prefill 中
       │     的某 chunk 可被暂缓，但已生成一半的序列也可被牺牲）。
       │
       ├── 常见策略（可组合）：
       │   · 最低优先级优先：仅抢占优先级更低的序列，保证高优不中断。
       │   · 最长剩余长度优先（Largest Remaining Time）：换出生成步数
       │     仍多的序列，因为其短期释放价值低，长期占用多。
       │   · 最早到达优先（FIFO）：先换出先来的，避免饥饿但欠精细。
       │   · 混合分： score = w1·(1/prio) + w2·(剩余步数) + w3·(已用计算)
       │
       │   选择后，将 Victim 序列状态标记为 SWAPPED，不再参与 decode
       │   直至换入。
       │
       └── 公平性考量：需避免同一条序列反复换入换出（颠簸），可设
           换出冷却期或按已换出次数惩罚。

       问题 2 · 换出操作如何保存序列状态并释放物理页？
       │
       ├── 换出对象：序列的全部 KV 缓存（包括已完成 prefill 的部分）。
       │   在 PagedAttention 管理下，即其所有物理页中的数据。
       │
       ├── 操作流程（每 Victim）：
       │   1. 暂停该序列的调度（从活跃集移除）。
       │   2. 遍历其 block_table，对于每个物理页：
       │          a. 若页内数据在 GPU 上且未被换出，将其 K/V 张量
       │             从 GPU HBM 拷贝到主机 CPU 内存中预分配的区域。
       │             保存形式可为原始 fp16 或压缩/量化后存储。
       │          b. 记录换出位置（CPU offset），并关联物理页 ID。
       │          c. 将物理页引用计数减一，页归还空闲池。
       │   3. 保留序列元数据：
       │        - block_table 逻辑→物理映射（换出后物理 ID 失效，需
       │          记录每个逻辑块换出到 CPU 的地址，或保留逻辑块大小信息）。
       │        - 已生成的 token 序列（用于恢复时重新 prefill 或跳过）。
       │        - 生成中的随机状态（如采样器的 RNG 状态）。
       │
       ├── 公式化换出成本：
       │        T_swap_out = N_blocks × (页数据量 / 传输带宽)
       │   一个 8k token 序列（B=16，d=128, 32 heads, fp16）
       │   约 8192/16 = 512 块，每块大小 ≈ 2×128×32×2×16 = 262144 字节，
       │   总传输约 128 MB，PCIe 带宽下约 2~4 ms。
       │
       └── 释放出的页直接注入空闲池，调度器可立即为新请求分配，
           使关键请求得以继续。此时引出换入时的恢复难题。

       问题 3 · 换入时如何恢复序列到可继续生成的状态？
       │
       ├── 两种恢复模式：
       │
       ├── (A) 从 CPU 重新加载 KV 缓存（精确保留）
       │   - 当显存再次充裕时，为该序列重新分配物理页（数量同换出前）。
       │   - 将 CPU 端保存的 K/V 数据逐页拷贝回新分配的物理页中，
       │     更新 block_table 的物理页 ID。
       │   - 恢复引用计数，序列加入活跃集，从断点继续 decode。
       │   - 代价：CPU→GPU 传输时间，与原换出对称。
       │
       ├── (B) 重计算 Prefill（丢弃 KV 缓存，仅保留 token ID）
       │   - 放弃缓存数据，但保留已生成的所有 token（prompt + 已生成部分）。
       │   - 恢复时，将序列视为一个新请求，用其完整 token 序列重新
       │     执行 prefill（可 chunked）重建 KV 缓存。
       │   - 重算后从断点之后继续 decode。
       │   - 计算成本 ∝ L_total² d，但无需 CPU 存储和传输 KV 缓存，
       │     节省 CPU 内存且实现简单。
       │   - 适用于缓存数据量极大、恢复延迟不敏感的序列。
       │
       ├── 选择判据：
       │       若 T_recompute < T_load + 2·T_transfer，则选重计算；
       │       否则选加载。短序列倾向重算，长序列优先重载以节省计算。
       │
       └── 序列恢复后，调度器将其按原有优先级重新纳入连续批处理，
           抢占流程完成闭环。

       问题 4 · 如何将抢占/换出集成到连续批处理与分页管理？
       │
       ├── 抢占触发时机：每次迭代结束，调度器检查空闲页数，
       │   若低于阈值（如总页数的 5%）且存在高优 pending 请求，
       │   在下次迭代构造 batch 之前执行抢占。
       │
       ├── 连续性保证：
       │   - 被抢占序列不会在迭代中途被粗暴终止，而是在迭代边界
       │     安全退出，保持所有数据结构一致。
       │   - 换出操作可与下一个迭代的 GPU 计算异步重叠（使用
       │     独立的 copy stream），避免延迟。
       │
       ├── 与写时复制（CoW）的交互：
       │   - 若被抢占序列与另一活跃序列共享前缀物理页，在减少
       │     引用计数时需谨慎：仅当计数降至 0 才可回收该页，
       │     否则保留给共享者使用。
       │   - 需换出时，共享页可能同时被多个序列引用，不能直接释放，
       │     除非只被该 victim 独占。通常只回收非共享页，共享页
       │     可保留或也拷贝换出但保留引用。
       │
       └── 总体效果：抢占使系统从“硬容量限制”升级为“弹性容量”，
           在过载时优雅降级，保障核心请求的延迟与吞吐 SLA，
           是云端 LLM 服务不可或缺的机制。

结论
       序列抢占与换出将有限的 GPU 显存转化为可超订的弹性资源，
       通过智能挑选 victim、高效换出/恢复以及与 PagedAttention 分页
       机制的深度耦合，使推理系统在极端负载下仍能维持高优先级服务的
       稳定，是连续批处理调度框架的最后韧性支柱。

       chunked-prefill(7)
