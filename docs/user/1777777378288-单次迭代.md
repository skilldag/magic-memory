LLM-ITERATION(7)            推理执行单元                LLM-ITERATION(7)

名称
       llm-iteration — 自回归推理的最小调度与执行单元，一次模型前向传播

概述
       单次迭代是 LLM 推理中不可再分的执行粒度：调度器在迭代边界
       重组批次，GPU 在迭代内完成一次完整前向计算并产出一个或多个
       token 的隐状态。正是对“迭代”这一概念的显式抽象，使得连续
       批处理、分块预填充、KV 缓存分页得以统一为同一调度周期。

描述
       传统上，一个请求被视作持续生成直到结束的“任务”，但高效服务
       需要将执行打散到更细的、可穿插的时间片。本章沿问题推导链
       ，解构“单次迭代”的内核、作用与引发的后续机制。

       问题 0 · 为什么必须将推理过程建模为离散的迭代？
       │
       ├── 自回归特性：每个新 token 需要前一步的 KV 状态，
       │   故一次前向即产出一个 token（或 prompt 的若干 token）。
       │   此即一个逻辑“步”。
       │
       ├── 若把一次请求的全部步封装为整体，则无法在步之间插入
       │   其他请求，导致类似传统 static batching 的阻塞。
       │   必须将每一步抽离为独立的计算单元 —— 迭代。
       │
       ├── 定义：
       │       一次迭代 = 一次完整的模型前向传播。
       │       输入：批次序列的当前 token + 历史 KV 缓存
       │       输出：各序列的下一个 token 的 logits（decode）
       │             或 prompt 块中所有位置的隐状态（prefill 块）
       │
       └── 关键：迭代结束时，调度器接管控制，可增删请求、移动
           内存、决定下一步，这是动态并发的基石。
           ↓
           问题：迭代内需要同时处理 prefill 和 decode，计算模式
           差异巨大，如何融合？

       问题 1 · 单次迭代内如何同时服务 prefill 与 decode？
       │
       ├── 迭代内计算概览（Transformer 层）：
       │       1. 输入嵌入/投影
       │       2. 注意力：QKV 投影 → 分页注意力计算
       │       3. FFN
       │       4. 输出头（仅对需要 logits 的位置）
       │
       ├── 两种序列在同一个 batch 中拼接：
       │       设批次内有 D 条 decode 序列（每条携带最后 1 token
       │       及完整 KV 缓存），P 条 prefill 序列（本次迭代可能
       │       只处理一个 chunk，含 C 个 token）。
       │       输入张量形状：
       │           input_ids: [D + P_chunk_tokens, ]
       │           block_tables 及 page 索引各自维护。
       │
       │   - 对 decode token：执行单 token 注意力（memory‑bound）
       │   - 对 prefill chunk：执行块内自注意力（compute‑bound）
       │   - PagedAttention 核通过各自的 block_table 统一寻址，
       │     在一次核调用中完成混合计算。
       │
       │   计算量近似（单层）：
       │       FLOPs = D · (4 d² + 2 d L_decode) +
       │               C · (4 d² + 2 d C)   （L_decode 为 decode 序列
       │                                        已缓存长度，C 为 chunk 大小）
       │       其中 d = head_dim × num_heads。
       │
       └── 为了保证 decode 延迟不受 prefill 过大影响，prefill 被
           切分为有限大小的 chunk。一次迭代最多处理一个 chunk。
           若 chunk 未完成，序列保持在 prefill 状态，下个迭代
           继续。这同时平滑了迭代计算时间。
           ↓
           问题：迭代的执行边界是否固定？如何保证迭代延迟可预测？

       问题 2 · 如何约束单次迭代的延迟上限？
       │
       ├── 子概念：最大 token 预算（Max Tokens per Iteration）
       │   - 调度器为每次迭代设定可处理的最大 token 总量 T_max。
       │        D + Σ C_i ≤ T_max
       │   - T_max 根据延迟 SLO 和 GPU 算力动态调整，防止某次
       │     迭代因大量 prefill 造成时间毛刺。
       │   - 剩余 prefill 请求排队，下个迭代优先。
       │
       ├── 实现： 迭代循环伪码
       │       while True:
       │           调度器选取请求构成 batch (满足 token 预算)
       │           batch = compose(D, P_chunks)
       │           output = model.forward(batch)
       │           更新序列状态、释放完成序列
       │           检查 KV 缓存压力，必要时抢占
       │
       └── 一次迭代的延迟约等于纯计算 + 访存时间，稳定在
           硬件能力带内，使得流式响应成为可能。
           ↓
           迭代间状态的持续性依赖 KV 缓存，引出其高效管理需求。

       问题 3 · 迭代如何驱动 KV 缓存的状态转换？
       │
       ├── 每次迭代后，所有活跃序列的 KV 缓存追加新 token 的 K、V。
       │   - decode 序列：追加 1 个位置的 K/V。
       │   - prefill 序列：写入 chunk 内各位置对应的 K/V。
       │   - 物理页按需分配（PagedAttention），引用计数更新。
       │
       ├── 迭代结束时，block_manager 执行：
       │       - 对完成序列：释放其物理页（引用计数减一）
       │       - 对分叉序列：写时复制保证不污染共享块
       │       - 为新 prefill 分配前缀块或共享已有块（前缀缓存）
       │
       └── 如此，每一次迭代既是计算的原子单位，也是内存管理的
           同步点。迭代 = 计算心脏 + 状态心跳。
           这形成了连续批处理 → PagedAttention → FlashAttention
           的完整调度循环。

结论
       单次迭代将自回归推理的串行生成分解为可交错、可中断、可联合
       调度的离散步，使 GPU 每一微秒的计算能力不被序列长度差异所
       空转。它是理解现代 LLM 服务系统时必须要掌握的原子概念。
