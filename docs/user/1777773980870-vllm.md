VLLM-ARCH(7)                 LLM 推理引擎                VLLM-ARCH(7)

名称
       vllm-arch — 高吞吐、近零内存碎片的 LLM 推理引擎核心原理

概述
       vLLM 通过 PageAttention 实现 KV 缓存分页管理，结合连续批处理调度
       及自动前缀缓存，将自回归推理的内存利用率提升至接近 100%，允许
       大幅扩大批次规模。

描述
       本手册以问题驱动层层推导，展示从内存瓶颈到完整推理系统的设计逻辑。
       推导采用树状缩进，每层解决一个问题并引出下一挑战。

问题 0 · 自回归生成的 KV 缓存为何成为瓶颈？
│
├── 预备：每生成一个 token，必须复用之前所有 token 的 Key 和 Value。
│   为免重复计算，通常将它们缓存在显存中，即 KV 缓存。
│
├── 传统分配：为每个序列预先分配最大长度 L_max 的连续内存。
│   - 内部碎片：实际长度 L_avg < L_max，空闲区段不可利用。
│   - 外部碎片：不同序列分配/释放交织，产生总量足够却无法分配连续块。
│   内存利用率 ≈ batch × L_avg / (batch × L_max) = L_avg / L_max。
│   例：L_max=8192, L_avg=512 → 利用率仅 6.25%。
│
└── 引出核心需求：必须像虚拟内存一样按需、离散地分配 KV 缓存。

问题 1 · 如何动态管理 KV 缓存以消灭碎片？
│
├── 子概念：PagedAttention（分页注意力）
│   - 将 KV 缓存分成固定大小 Page（块），每块包含 B 个 token 的 K/V 向量。
│   - 逻辑块序列 → 物理块映射表： block_table[seq_id][logical_block_idx] = physical_block
│   - 物理块按需从空闲池分配，不再要求连续。
│
├── 结果
│   - 外部碎片消失。内部碎片仅出现在末尾块（≤ B-1 个 token 浪费）。
│   - 可在同等显存下支撑更大 batch，吞吐近似反比于内存浪费。
│
└── 新问题：注意力的计算需要依次访问非连续的物理块，
    朴素做法是 gather→拼接→调用标准 MatMul，开销过大。
    ↓
问题 2 · 如何高效计算分页 KV 的注意力？
│
├── 子概念：定制 PagedAttention 核（GPU Kernel）
│   - 融合操作：一次核函数完成 block table 查表、K/V 读取、注意力计算。
│   - 采用类 FlashAttention 的分块策略：将 Q 分成小块，逐块迭代所有逻辑 KV 块。
│     伪码：
│         for Q_block in Q_blocks:
│             acc = 0, l = 0, m = -inf
│             for logical_block in seq:
│                 physical = block_table[logical_block]
│                 K_block, V_block = load(physical)
│                 S = Q_block @ K_block^T / sqrt(d)
│                 m_new = max(m, row_max(S))
│                 acc = exp(m - m_new)*acc + exp(S - m_new) @ V_block
│                 l = exp(m - m_new)*l + row_sum(exp(S - m_new))
│                 m = m_new
│             O_block = acc / l
│   - 不构造完整 N×N 矩阵，用 SRAM 缓存块，访存量最优。
│
└── 新问题：请求长度不一、动态到达，如何调度 GPU 以避免空闲气泡？
    ↓
问题 3 · 如何调度动态批次实现最大吞吐？
│
├── 子概念：连续批处理（Continuous Batching） + 迭代级调度
│   - 传统 batch：等到 batch 内全部完成再取新请求 → GPU 利用率剧烈抖动。
│   - vLLM：每次模型 forward（一个 iteration）动态组织 batch。
│       调度器选取：
│         · 几条 decode 请求（每请求 1 token）
│         · 若干 prefill 请求，允许分块执行（chunked prefill）。
│   - 一次迭代混合 prefill 与 decode，PagedAttention 核通过不同
│     序列各自的 block_table 正确寻址。
│
├── 物理块调度：块分配器在 iteration 边界为 prefill 新 token 预留物理块，
│   若内存不足可抢占低优先级序列，释放其物理块。
│
└── 新问题：众多请求共享相同前缀（系统提示、少样本示例），
    导致重复存储与重复计算。
    ↓
问题 4 · 如何自动共享公共前缀的 KV 块？
│
├── 子概念：自动前缀缓存（Automatic Prefix Caching）
│   - 每生成一个逻辑块的 K/V 时，计算其内容哈希（基于 token ID 序列）。
│   - 全局哈希表： hash → 物理块引用。
│   - 新请求匹配到相同哈希时，直接增加引用计数，不分配新块、不重新计算。
│   - 写时复制（Copy‑on‑Write）：当某共享块因序列分叉需要写入时，
│     复制该物理块，保证隔离。
│
├── 效果
│   - 消除前缀的存储与 prefill 计算冗余，进一步降低首 token 延迟。
│   - 对多轮对话和大批量同 prompt 场景提升显著。
│
└── 闭环：PagedAttention + 连续批处理 + 前缀缓存，
    构成 vLLM 近乎理想的内存与调度体系，将 LLM 推理的吞吐推至硬件极限。
