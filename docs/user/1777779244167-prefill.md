PREFILL(7)               Transformer 推理阶段               PREFILL(7)

名称
       prefill — 将输入 prompt 一次或分块编码为 KV 缓存与首个 token
                状态的高并行处理阶段

概述
       Prefill 是每次自回归生成的起始阶段，负责将用户输入的完整 prompt
       并行通过 Transformer 层并产出初始 KV 缓存，使模型获得对该提示的
       全部上下文感知，随后进入逐 token 的 decode 阶段。通过分块预填充
       可与 decode 混合调度，消除长 prompt 引发的计算毛刺。

描述
       本手册沿问题链推导 prefill 的必要性、计算特性、与 decode 的
       协同以及化为分块操作的进化路径。

       问题 0 · 为什么 decode 无法独立完成对新 prompt 的理解？
       │
       ├── 自回归解码的核心循环：
       │       输入 token x_t，结合历史 KV 缓存，输出 logits 决定 x_{t+1}。
       │       此过程每一个 step 仅能“看见”之前已生成的 token。
       │
       ├── 若没有 prefill，直接以 decode 方式处理 prompt：
       │       必须在 <s> 后逐 token 输入 prompt 的每个字符，每一步
       │       仅处理一个 token，导致两个致命问题：
       │       ① 延迟：需要 N 次串行 forward 才能编码长度为 N 的
       │           prompt，响应首 token 的时间与 prompt 长度成正比。
       │       ② 浪费并行性：自注意力将 prompt 的所有 token 视为
       │           序列内成员，而 decode 一次只送入一个 token，无法利用
       │           GPU 并行计算 prompt 内所有 token 的注意力。
       │
       ├── 对比公式（仅计注意力部分）：
       │       Prefill 一次性计算 prompt 的全自注意力：
       │           Q,K,V ∈ R^{N×d} → O = softmax(Q K^T / √d) V
       │           计算量 ∝ N² d，但高度并行，实际耗时约为 O(N²/B) 量级。
       │       Decode 处理 prompt 需 N 步，第 i 步计算量 ∝ i d，
       │           总耗时 ∝ N² d，但完全串行，延迟无法通过并行摊薄。
       │
       └── 因此，设计一个专门的阶段，将 prompt 一次性（或分大块）传入
           模型完成预填充，是必然选择。 此阶段即 prefill。

       问题 1 · prefill 阶段内部如何计算并将状态传递给 decode？
       │
       ├── Prefill 的执行过程（单层 Transformer）：
       │       给定 prompt_ids shape [1, N]（batch=1 示例）
       │       1. 输入嵌入 × N
       │       2. 对所有位置并行投影：Q, K, V = proj(prompt_ids)
       │       3. 无掩码全自注意力：允许每个 token 关注 prompt 内所有 token。
       │          输出 O ∈ R^{N×d}。
       │       4. FFN 等后续模块。
       │       5. 将每一层的 K, V 张量按序列位置切片，存入 KV 缓存。
       │          - 若使用 PagedAttention，则将 K/V 按块写入物理页，
       │            并记录 block_table。
       │       6. 仅保留最后位置的隐状态用于产生第一个生成 token 的 logits
       │          （或保留全部位置，但解码仅需最后 token 状态）。
       │
       ├── Prefill 结束后的状态转移：
       │       - KV 缓存中已存有全部 N 个 prompt token 的键值对。
       │       - 序列状态由 prefill 转为 decode，后续每次迭代只送入
       │         新生成的 token，利用已有 KV 缓存计算自注意力。
       │
       └── 这引出新挑战：prefill 计算量巨大（O(N² d)），若将长 prompt
           一次性提交，单次迭代延迟极高，阻塞其他 decode 序列。
           → 如何使 prefill 的延迟变得平滑可控？

       问题 2 · 如何消除长 prefill 导致的延迟毛刺与批次中断？
       │
       ├── 子概念：Chunked Prefill（分块预填充）
       │   - 将长 prompt 切分为固定大小的 token 块（chunk），
       │     例如每块 C=512 token。
       │   - 每个迭代仅处理一个 chunk 的 prefill，而不是整条 prompt。
       │   - 处理流程：
       │        第 1 次迭代：prefill chunk 0 → 写入 K/V 块 → 状态置为
       │                     prefill 进行中。
       │        第 2 次迭代：继续 prefill chunk 1，同时该序列可独占新
       │                     分配的 KV 块，累积 cache。
       │        ...
       │        最后 chunk 完成 → 序列转入 decode。
       │
       ├── 延迟约束与调度融合：
       │   - 设定每次迭代最大 token 预算 T_max。
       │   - 单次迭代内，chunk 大小 + 同时服务的 decode token 数 ≤ T_max。
       │   - prefill 不再是一堵不可打断的墙，而是像 decode 一样拆成
       │     多次迭代穿插执行，使系统延迟曲线极为平缓。
       │
       └── Chunked prefill 使长 prompt 的首次生成延迟从 O(N²) 串行
           降为 O(N) 迭代 × 恒定块计算，且完美融入连续批处理调度。
           由此，prefill 与 decode 从割裂的两个阶段变为同一迭代循环
           中交织的任务，为极致 GPU 利用率铺平道路。

       问题 3 · prefill 与 decode 混合时如何保持 KV 缓存一致性？
       │
       ├── 核心规则：prefill chunk 处理的新 token，其 K/V 在写入物理
       │   页时遵循与 decode 完全相同的 PagedAttention 机制。
       │   - block_table 在 prefill 开始时预留足够逻辑块（N/B 向上取整），
       │     物理页随 chunk 按需分配。
       │   - 每次迭代后，block_manager 追加新页或复用已有 chunk 的页，
       │     引用计数更新。
       │
       ├── 注意力掩码适配：
       │   - 对于 prefill chunk 内的 token，使用因果掩码（自回归限制）。
       │   - 对于 decode token，扩展掩码使其可见包括最新 prefill chunk
       │     产生的 KV（若有混合迭代）。PagedAttention 核已内建逻辑。
       │
       └── 最终，prefill 被解构为可变粒度的、可抢占的、与 decode 同调度
           的计算任务，成为复杂推理负载中灵活的一环。

结论
       Prefill 将输入 prompt 高效编码为 KV 缓存状态，以并行优势大幅
       降低首 token 延迟。经由分块化和迭代级混合调度，prefill 不再
       是延迟瓶颈，而是与 decode 对流协同的透明阶段，共同构建现代
       LLM 推理系统的高吞吐核心。
