SEQUENCE-GENERATION(7)        LLM 基础概念              SEQUENCE-GENERATION(7)

名称
       sequence-generation — 从无到有地逐 token 产生文本序列的完整过程

概述
       序列生成是语言模型从给定输入（可能为空）出发，反复预测下一
       个 token 并累积为完整文本的推理范式。它以自回归解码为执行引擎，
       由 KV 缓存携带状态，受批次调度和内存管理的系统壳体包裹，构成
       现代 LLM 服务化的直接界面。

描述
       本手册沿层层递进的问题链，从概率建模、解码循环、状态缓存、
       到并发调度，构建序列生成的全景理解。

       问题 0 · 模型如何知道该生成什么样的序列？
       │
       ├── 基础：语言模型学习整个序列的概率 P(x₁,...,x_T)。
       │   - 通过链式法则，将联合概率分解为逐步条件概率之积：
       │         P(x) = ∏_{t=1}^T P(x_t | x_{<t})
       │   - 训练目标：最小化负对数似然（交叉熵），使模型在每个位置
       │     都成为该上下文中下一个 token 的最优预测器。
       │   - 详见 joint-distribution(7), chain-rule(7), autoregressive(7)。
       │
       ├── 推理时，模型由用户提供的 prompt x_{<t} 激发，输出对 x_t 的
       │   概率分布 P(x_t | x_{<t})。将此分布解码为具体 token，即
       │   完成了序列推进的第一步。
       │
       └── 由此引出：有了条件分布，具体如何一步一步产生序列？
           即解码策略与串行循环的问题。

       问题 1 · 有了模型输出后，如何选择一个 token 并继续下去？
       │
       ├── 自回归解码循环（autoregressive-decoding(7)）：
       │       重复执行直至遇到结束符 <eos> 或达到最大长度：
       │           1. 将当前序列（最初仅 prompt）输入模型，得到 logits。
       │           2. 使用选定的解码策略将 logits 映射为下一个 token。
       │           3. 将新 token 拼接到序列末尾。
       │
       ├── 常见解码策略（决定从分布到 token 的映射规则）：
       │       · 贪心 (Greedy): x_t = argmax P(x_t | x_{<t})
       │       · 温度采样: 调节分布尖锐度，增加随机性。
       │       · Top‑k / Top‑p (Nucleus): 从截断的候选集中随机采样，
       │         平衡质量与多样性。
       │       · 束搜索 (Beam Search): 保持多个假设同时推进。
       │   策略仅影响 token 选择，不影响底层模型迭代结构。
       │
       └── 但每次迭代需要让模型“看到”所有历史 token，若每步都
           重新编码整个序列，计算量将随长度平方增长。如何避免？

       问题 2 · 如何在逐 token 生成时免去对历史的重复计算？
       │
       ├── 子概念：KV 缓存（kv-cache(7)）
       │   - 每生成一个 token 后，将该 token 经 Transformer 层产生的
       │     Key 和 Value 张量持久保留在显存中。
       │   - 下个迭代只需要计算新 token 的 Q, K, V，并从缓存中读取
       │     所有历史 K, V 进行注意力计算。
       │   - 投影计算量由 O(t·d²) 降为 O(d²)，与长度解耦。
       │
       ├── KV 缓存的物理增长：
       │   - 随序列增长，缓存呈线性膨胀，成为显存占用的主要来源。
       │   - 这立即引发内存瓶颈，尤其多请求并发时。
       │
       └── 推动问题：如何在有限的显存中高效存储与利用 KV 缓存？

       问题 3 · 显存不足以容纳所有序列的完整 KV 缓存时怎么办？
       │
       ├── 解决方案树（可叠加）：
       │
       ├── (A) 架构压缩：
       │       - MQA / GQA：多查询或分组查询注意力，减少 KV 头数。
       │       - 滑动窗口：仅保留最近 W 个 token 的缓存，丢弃远端。
       │         缓存大小与总长度解耦。
       │
       ├── (B) 分页管理 — PagedAttention（pageattention(7)）：
       │       - 将 KV 缓存划分为固定大小的 Page（块）。
       │       - 序列按需从空闲池分配物理页，通过页表映射访问。
       │       - 消除外部碎片，实现近 100% 显存利用率。
       │
       ├── (C) 量化缓存：
       │       - 以 INT8/INT4 存储 K/V，计算时反量化为 FP16，
       │         体积压缩 2~4 倍。
       │
       └── 内存瓶颈缓解后，新的瓶颈转移到调度：如何让同一块 GPU
           同时服务数百个处于不同生成进度的请求？

       问题 4 · 多请求并发时，如何优雅地调度生成步骤？
       │
       ├── 挑战：不同请求长度、进度各异。静态批次会因短板请求
       │   造成 GPU 大量空闲。
       │
       ├── 子概念：连续批处理与迭代级调度（continuous-batching(7),
       │   llm-iteration(7)）
       │   - 将整个序列生成过程拆分为原子“迭代”（一次模型前向）。
       │   - 每次迭代前动态构建 batch：
       │        · 携带所有活跃的 decode 序列（各 1 token）
       │        · 尽可能融入新的 prefill 请求（可用 chunked prefill
       │          平滑其计算量）
       │   - 任一序列生成结束，立即释放其物理页并退出。
       │   - GPU 在每次迭代都接近满载，无空闲气泡。
       │
       ├── 弹性层：序列抢占与换出（sequence-preemption(7)）
       │   - 显存极端不足时，低优先级序列 KV 缓存可换出至 CPU 或丢弃，
       │     腾挪空间给高优先级请求，后续恢复或重算。
       │
       └── 最后，系统中经常出现大量共享同一前缀的请求（如相同的
           system prompt）。能否避免为它们各自缓存一份相同的 K/V？

       问题 5 · 如何利用请求间的公共前缀减少存储与计算？
       │
       ├── 子概念：自动前缀缓存（automatic-prefix-caching(7)）
       │   - 为每个已缓存满的物理页计算 token 序列的哈希值。
       │   - 新请求 prefill 时，若匹配哈希，则直接增加物理页引用
       │     计数，跳过该块的注意力计算。
       │   - 写时复制保证当共享块因序列分叉被修改时，不影响其他请求。
       │
       └── 这使公共前缀仅存储一份，计算仅执行一次，极大压缩了
           批量相似 prompt 的资源开销。

       闭合回路
       │
       └── 至此，序列生成的全栈图景被衔接起来：
               概率基座（自回归 + 链式法则）
               → 解码循环（采样策略 + KV 缓存）
               → 内存优化（分页 / 压缩 / 滑动窗口）
               → 并发调度（连续批处理 + Chunked Prefill + 抢占）
               → 共享消除（前缀缓存）
           每一层都解决了上一层遗留的瓶颈，最终实现高吞吐低延迟的
           长序列生成服务。

       pageattention(7), continuous-batching(7), prefill(7),
       automatic-prefix-caching(7), llm-iteration(7)
