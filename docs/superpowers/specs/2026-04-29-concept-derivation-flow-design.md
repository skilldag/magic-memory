# 概念推导层级展开流程 — 设计文档

> 本设计是对 `design.md`（问题驱动推导学习）的补充，聚焦于「概念→子概念」的层级展开流程。
> 回答的核心问题：用户如何从一个概念自然地过渡到其子概念的推导？
>
> ⚠️ 关键约束：用户首次进入一个概念时，对该概念的「过程」是未知的。
> ⚠️ 第一原则：第一次接触必须由**好奇驱动**，不是记忆驱动。记忆是负担。

---

## 1. 核心理念：认知循环的嵌套

```
┌─────────────────────────────────────────────┐
│  认知循环 N（当前概念）                        │
│                                              │
│  过程 → 矛盾 → 问题 → 推导 → 揭晓概念          │
│                                              │
│  揭晓后 → 自然产生新问题：「那它的内部呢？」       │
└─────────────────────────────────┬───────────┘
                                  │ 过渡
                                  ↓
┌─────────────────────────────────────────────┐
│  认知循环 N+1（子概念）                        │
│                                              │
│  新过程 → 新矛盾 → 新问题 → 新推导 → 揭晓子概念  │
└─────────────────────────────────────────────┘
```

每个概念的推导都遵循 `design.md` §1.1 的认知链条（过程→矛盾→问题→推导→揭晓），层级展开只是这个链条的递归嵌套。

### 整体策略

先了解 vLLM 整体（根概念），逐步展开子概念，再展开子概念的子概念。

### 核心矛盾：空白画板 + 测试感

`design.md` 假设用户进入画板时已经知道「过程」的轮廓。但新手不知道。同时，第一次接触不能有「测试感」——选择题问答本质上仍然是让用户回忆，是在测试。

正确的第一次接触应该是：**展示，不提问。让用户在探索中产生好奇，好奇驱动深入。**

---

## 2. 探索式导览：好奇驱动的第一次接触

### 2.1 设计原则

```
第一次进入 = 探索模式（看一个故事，产生好奇）
第二次进入 = 推导模式（空白画板，验证理解）
```

**探索模式不是测试**。用户不需要回答任何问题，不需要回忆任何东西。只需要看、点、探索。

### 2.2 探索流程

第一次双击进入概念画板时，不展示空白画板——展示一个**可交互的过程动画**：

```
┌──────────────────────────────────────────────────────┐
│  vLLM  ·  请求处理过程                                  │
│                                                        │
│  一个用户请求来到了 vLLM...                              │
│                                                        │
│               ┌──────────────┐                         │
│   请求 ──────→│  OpenAI API  │                         │
│  "巴黎是首都？" └──────────────┘                         │
│                     ↓                                   │
│               ┌──────────────┐                         │
│               │  Engine API  │                         │
│               └──────────────┘                         │
│                     ↓                                   │
│               ┌──────────────┐     ┌──────────────┐    │
│               │  Scheduler   │────→│   模型运行...  │    │
│               └──────────────┘     └──────────────┘    │
│                                                        │
│  ● 点击任意步骤查看发生了什么                              │
│  ● 进度: 1/3                                            │
│                                                        │
└──────────────────────────────────────────────────────────┘
```

关键是：**用户不是在回答问题，而是在观看一个过程，并在感兴趣的地方停下来深入。**

### 2.3 交互方式

| 交互 | 行为 | 驱动 |
|------|------|------|
| 自动播放 | 请求流自动走过 3-5 个主要步骤，每个步骤高亮 + 一句话说明 | 被动接收，建立框架 |
| 悬停暂停 | 鼠标停在某个步骤上→动画暂停→显示该步骤的简要说明 | 好奇驱动 |
| 点击深入 | 点击某个步骤→展开该步骤的详细视图→进入该子概念的探索入口 | 兴趣驱动 |
| 拖动时间轴 | 底部进度条可拖动，回到之前看过的步骤 | 自主控制 |

### 2.4 从探索到深入：自然的好奇过渡

在探索过程中，当用户点击某个步骤时：

```
┌──────────────────────────────────────┐
│  用户停在「Scheduler」步骤              │
│                                      │
│  ┌──── 展开 ──────────────────────┐  │
│  │                                │  │
│  │  Scheduler 负责决定：           │  │
│  │  - 下一个执行哪个请求            │  │
│  │  - 如何最大化 GPU 利用率         │  │
│  │  - 请求太多时怎么排队            │  │
│  │                                │  │
│  │  [🔍 探索 Scheduler 内部]       │  │
│  │                                │  │
│  └────────────────────────────────┘  │
│                                      │
│  点击 [探索内部] → 进入 Scheduler     │
│  子概念的探索模式（递归）              │
└──────────────────────────────────────┘
```

点击 [探索内部] 是进入子概念的入口。这个动作是**用户自主决定的**——不是系统让他学，而是他好奇「Scheduler 里面是什么样的」。

### 2.5 探索结束后的两种出口

方式 A：全部看完 → 自然过渡到推导模式

```
全部步骤浏览完后：
「你已经了解了 vLLM 请求处理的大致流程。
  现在试试在画板上自己推导这个流程？」

  [进入推导模式]
```

方式 B：中途退出 → 回到图谱

探索进度被记录，下次进入可以继续或直接跳转到推导模式。

### 2.6 探索模式的视觉语言

探索模式与推导模式的视觉区分：

| 模式 | 背景 | 节点样式 | 交互方式 |
|------|------|----------|----------|
| 探索模式 | 深色/半透明背景，聚焦动画 | 发光边缘，可点击展开 | 自动播放 + 点击深入 |
| 推导模式 | 默认画板背景 | 标准 ReactFlow 节点 | 拖拽 + 连线 + 提交 |

两种模式在同一个画板中切换，共用面包屑和进度树。

## 3. 子概念过渡：从探索到探索

### 3.1 过渡入口

当用户在探索模式下点击某个步骤的 [探索内部] 时：

```
┌── 父概念探索模式 ─────────────────────┐
│                                      │
│  Scheduler 步骤                       │
│  [🔍 探索 Scheduler 内部]  ← 用户点击  │
│                                      │
└──────────┬───────────────────────────┘
           │
           ↓
┌── 子概念探索模式 ─────────────────────┐
│                                      │
│  进入时顶部显示上下文：                   │
│  「你在 vLLM 请求流程中看到了             │
│    Scheduler 负责调度请求。               │
│    现在来看看它内部是怎么工作的。」          │
│                                      │
│  然后播放 Scheduler 的内部过程动画...    │
│                                      │
└──────────────────────────────────────┘
```

关键点：过渡后进入的仍然是**探索模式**（不是推导模式）。子概念的第一遍也是好奇驱动。

### 3.2 从探索到推导的转换

用户第一次探索完一个概念的所有步骤后，才**解锁**该概念的推导模式：

```
探索完成 → 「你已经了解了 X 的过程。想试试自己推导一遍吗？」

  [进入推导模式] ← 进入 design.md 的空白画板 + 对照验证流程
  [再看一遍]      ← 重新探索
```

解锁后：
- 从图谱双击进入 → 直接进入推导模式（空白画板）
- 从 ComparisonPanel 的 gap 进入 → 进入推导模式（带过渡上下文）

### 3.3 推导模式的 GapItem（基于 design.md §4）

当用户提交推导后，ComparisonPanel 展示 gap：

```
⚡ 「Scheduler 如何决定下一个执行哪个请求？」 → [探索 FCFS/优先级调度]
```

GapItem 携带上下文：

```typescript
interface GapItem {
  conceptId: string
  label: string
  triggerStep: string        // 父推导的哪一步
  entryContext: string       // 一句话上下文
  /** 如果是未探索过的子概念 → true，点击后进入探索模式 */
  needsExploration: boolean
}
```

- 如果子概念**未被探索过** → 点击后进入探索模式（好奇驱动）
- 如果子概念**已探索过** → 点击后进入推导模式（验证理解）

## 4. 回溯与结构感知

### 4.1 面包屑导航

ProcessCanvas 顶部工具栏路径指示：

```
图谱  >  vLLM [推导]  >  Scheduler [探索]  >  FCFS [推导]
```

方括号标注当前是探索模式还是推导模式。

### 4.2 层级进度树

```
vLLM ────────── 推导完成 ──
├─ VllmConfig  ✅ 已掌握
├─ Tensor      ✅ 已掌握
├─ Scheduler   🔄 探索中 (当前)
│  ├─ FCFS          ⬜ 未开始
│  ├─ Priority      ⬜ 未开始
│  └─ Continuous    ✅ 已掌握
└─ Sampler     ⬜ 未开始
```

状态颜色：
- ⬜ 灰暗 → 从未进入过（既没探索也没推导）
- 🔄 微光 → 探索过但未推导
- ⚡ 脉动光 → 推导后有差异待探索
- ✅ 稳定光 → 推导完成且无 gap

### 4.3 自动保存

- 探索模式：保存当前播放位置（下次继续）
- 推导模式：保存 CanvasState（画布状态）
- 每个 conceptId 独立存储

## 5. 完整用户旅程

```
Step 1:  双击 vLLM 节点（首次）→ 进入探索模式
Step 2:  自动播放 vLLM 请求处理流程动画（5 个步骤）
Step 3:  用户对 Scheduler 步骤产生好奇 → 点击展开
Step 4:  看到「探索内部」按钮 → 点击
Step 5:  进入 Scheduler 的探索模式
         顶部上下文：「在 vLLM 请求流程中，Scheduler 负责调度...」
Step 6:  Scheduler 探索完 → 解锁推导模式
Step 7:  用户选择「进入推导模式」
Step 8:  进入空白画板（Scheduler 推导）→ 拖拽、连线、提交
Step 9:  ComparisonPanel 显示 gap
         ⚡ 「请求多了怎么排？→ FCFS」[探索]（FCFS 未探索过）
Step 10: 点击 → FCFS 探索模式 → 理解 FCFS
Step 11: 返回 Scheduler 推导 → 重新提交 → gap 关闭
Step 12: 返回 vLLM → 处理剩余 gap...
```

## 6. 数据模型

```typescript
// 探索模式状态
interface ExplorationState {
  conceptId: string
  completed: boolean           // 是否完整看完一遍
  currentStepIndex: number     // 播放位置
  exploredSteps: string[]      // 点过 [探索内部] 的步骤
}

// GapItem（增强版）
interface GapItem {
  conceptId: string
  label: string
  triggerStep: string
  entryContext: string
  needsExploration: boolean    // 是否未探索过
}

// Concept 层级扩展
interface Concept {
  hierarchy: {
    parentId: string | null
    level: number
    order: number
  }
}

// 画板 store
interface CanvasStore {
  canvasHistory: { conceptId: string; mode: 'explore' | 'derive' }[]
  canvasStates: Map<string, CanvasState>
  explorationStates: Map<string, ExplorationState>
  hierarchyProgress: HierarchyProgress
}
```

## 7. 与 design.md 的关系

| 本设计内容 | 对应 design.md | 关系 |
|-----------|----------------|------|
| 探索模式 | 新增前置步骤 | 独立新增，不修改现有流程 |
| 推导模式 | §3 过程画板 + §4 对照验证 | 直接复用现有流程 |
| 探索→推导解锁 | — | 新增转换机制 |
| GapItem 增强 | §4 对照验证 | 扩展 |
| 面包屑 + 进度树 | §3 过程画板 | 扩展 |

---

## 8. 不做的事

- 探索模式不包含任何测试/问答/选择题
- 不锁定任何功能（用户可随时退出探索进入推导）
- 不改变 comparisonPanel 的交互
- 不修改知识图谱的渲染
- 不走完探索也能进入推导（只是没有上下文参考）
