# NixlConnector(7) — vLLM KV Cache Transfer Connector

## NAME

`vllm-NixlConnector` — 面向 vLLM V1 分离式预填充的完全异步 KV 缓存传输连接器，基于 NVIDIA NIXL 库实现跨进程 RDMA 级 GPU 显存零拷贝传输。-[-1](https://docs.vllm.com.cn/en/latest/features/nixl_connector_usage/#__codelineno-1-1)

## SYNOPSIS

```python
from vllm.distributed.kv_transfer.kv_connector.v1.nixl import NixlConnector
```

```text
vllm serve --kv-transfer-config '{"kv_connector":"NixlConnector"}'
```

## DESCRIPTION

```text
Q0: 将 LLM 推理的 Prefill 与 Decode 阶段部署在不同 GPU 实例上时，
    如何将 Prefill 端产生的大规模 KV Cache 高效送达 Decode 端？
```

分离式预填充（disaggregated prefilling）架构将 Prefill 阶段（计算密集、延迟敏感）与 Decode 阶段（访存密集、吞吐敏感）物理剥离[-5](https://deepwiki.com/vllm-project/vllm/9.4-communication-infrastructure)[-24](https://deepwiki.com/vllm-project/vllm/9.4-kv-cache-transfer-and-disaggregated-serving)。两个阶段部署在独立 GPU 实例上，中间横跨进程边界，甚至跨越节点。

核心矛盾：

- KV Cache 体量极大（典型场景可达数十 GB），必须传输至 Decode 端方可保证语义等价。
- 拷贝路径若途经 CPU 内存将引入 `O(N)` 的 PCIe 中转开销，抵消分离部署的吞吐收益。

```text
┌─────────────┐            ┌─────────────┐
│  Prefill     │  KV Cache │  Decode      │
│  Instance    │ ─────?──→ │  Instance    │
│  (Producer)  │  路径?    │  (Consumer)  │
└─────────────┘            └─────────────┘
```

## PROBLEM DECOMPOSITION: Q0 → Root Cause → Q1

```text
Q0 (KV 传输): 跨进程传输大规模 KV Cache

  root cause:
    ├─ Mem(host) ∉ {GPU VRAM₁, GPU VRAM₂}  —  两端 GPU 显存地址空间相互隔离
    ├─ 传统 memcpy 路径:  GPU₁ → CPU → GPU₂
    │   Latency ≈ 2·T_pcie(d)  —  两次 PCIe 往返
    └─ NCCL 集体操作粒度:  all-gather / broadcast 面向全体 rank
        无法做 per-request、per-block 的细粒度异步传输

  → Q1: 如何建立跨实例 GPU 显存的直接数据通路，
        并以全异步方式驱动 per-block 传输？
```

## Q1 → NIXL 核心抽象: Agent + Memory Registration + Transfer Descriptor

```text
Q1 (跨 GPU 直接通路 + 异步驱动)

  sub-concept 1: NIXL Agent — 分布式 RAII 传输上下文

    ┌─────────────────────────────────────────────────────┐
    │  nixlAgent                                         │
    │    ├─ 管理本进程可见的 GPU/CPU/NVMe 内存区域          │
    │    ├─ 通过 side-channel 与对端 Agent 交换元数据        │
    │    │  (ZMQ/shared-memory 握手, 参见 env VLLM_NIXL_   │
    │    │   SIDE_CHANNEL_PORT[reference:4])               │
    │    └─ 根据 backend 路由选择合适的物理传输路径:         │
    │       - NVLink (intra-node)                          │
    │       - InfiniBand / RoCE v2 (inter-node)            │
    │       - GPU Direct Storage (GDS, to NVMe)[reference:5]│
    └─────────────────────────────────────────────────────┘

    公式:

      agent::=⟨mem_map, backend_registry, side_channel⟩
      side_channel::=ZMQ | shm | ...

    NIXL 将异构设备统一抽象为 memory segment，
    上层不感知底层是 HBM、DRAM、NVMe 还是对象存储。[reference:6]

  sub-concept 2: Memory Registration — 将 vLLM Paged KV Buffer 暴露为 NIXL 可寻址段

    在 GPU Worker 初始化阶段:

      buf_addr = kv_cache.blocks.ptr()           // vLLM paged KV 首地址
      NixlConnector.register_memory(buf_addr)    // → agent.register()

    register_memory() 返回:
      descriptor_struct {
        addr:   GPU_virtual_address        // GPU 虚拟地址
        len:    total_kv_cache_capacity    // 以字节计
        key:    unique_memory_handle       // NIXL 全局唯一 ID
      }

    原理:
      对每个 GPU Worker，将 paged KV buffer 作为单一 registered
      memory region 托管给 NIXL Agent。Agent 持有该 region 的物理
      地址映射，使得后续传输无需重复注册。

  sub-concept 3: Transfer Descriptor — 无状态、可等待的异步操作句柄

    传输请求由 <src_block, dst_block, n_tokens> 三元组参数化:

      transfer_t = agent.create_transfer(                  // 非阻塞
        src_segment, src_offset,
        dst_segment, dst_offset,
        n_bytes
      )

    NixlConnector 内部将 transfer_t 入队，
    在 decode forward 的同步点调用:

      status = transfer_t.wait()

    公式:

      state_machine(transfer_t) ::=
        CREATED → SUBMITTED → IN_FLIGHT → COMPLETED

    NIXL 保证 backends 均为非阻塞 API，
    用户可在传输未完成期间持续执行模型计算。[reference:7]

  → Q2: 上述 agent 与 memory registration 是基础设施，
        但全异步仅靠单个 transfer descriptor 不够 ——
        多请求如何并发？Prefill 按层产出 KV 如何流入 decode？
```

## Q2 → 双通道调度模型: Scheduler 侧 vs Worker 侧

```text
Q2 (多请求并发调度 + 按层传输)

  NixlConnector 本身是 thin facade，
  将实际逻辑委托给两套角色实例:[reference:8][reference:9]

    ┌──────────────────────────────────────────────────────┐
    │  NixlConnector                                       │
    │    ├─ Scheduler-side: NixlConnector_Scheduler       │
    │    │   ├─ 维护 per-request metadata map              │
    │    │   ├─ 决定哪些 block 需 send / recv               │
    │    │   └─ 下发 transfer 命令到 Worker                 │
    │    │                                                  │
    │    └─ Worker-side: NixlConnector_Worker  (× N_GPU)   │
    │        ├─ 持有 registered KV buffer handle           │
    │        ├─ 执行 start_save_layer / start_load_layer   │
    │        └─ 在 forward 关键路径 poll transfer status   │
    └──────────────────────────────────────────────────────┘

  关键接口 (简写):

    // —— Prefill 端 (Producer) ——
    start_save_layer(layer_id, block_tokens[], kv_tensors[])
      // Attention kernel 完成后调用，将当前 layer 全部 KV
      // 插入异步发送队列

    // —— Decode 端 (Consumer) ——
    start_load_layer(layer_id, block_tokens[])
      // 在对应 layer 的 attention forward 前调用，
      // 等待该 layer 的 KV cache 接收完成

  sub-concept: Layer-Ordered Pipelining

    设模型有 L 层 transformer blocks。
    Producer 端逐层生成 KV (layer 0, 1, …, L-1) 并逐层发送；
    Decode 端按相同顺序逐层等待。

    时间线:

      Producer:  ─[attn L0]─[send L0]─[attn L1]─[send L1]─···
      Consumer:              ─[recv L0]─[attn L0]─[recv L1]─[attn L1]···

    Pipeline 重叠因子:

      η_overlap = T_attn / max(T_send, T_recv)

    当 T_send ≪ T_attn 时，η_overlap → 1，传输几乎完全
    隐藏在计算背后。

  → Q3: 逐层流水线解决了时间重叠。但跨网络传输时，
        metadata 如何协商？ 两端的 KV layout 如何保证一致？
```

## Q3 → Metadata Side-Channel + 兼容性握手

```text
Q3 (跨实例 metadata 协商)

  sub-concept 1: 握手阶段 — 兼容性哈希校验

    Prefill 与 Decode 实例在建立连接时交换兼容性记录:[reference:10]

      compat_record {
        vllm_version,          // vLLM 版本
        nixl_connector_version,// 连接器版本
        model_arch,            // 模型架构标识
        dtype,                 // 参数/缓存数据类型
        num_kv_heads,          // KV 注意力头数
        head_size,             // 每头维度
        num_hidden_layers,     // 隐藏层数
        attn_backend,          // 注意力后端 (FLASH_ATTN|FLASHINFER|...)
        cache_dtype,           // KV 缓存 dtype
      }

    若两侧哈希不匹配则连接拒绝 — — 保证系统语义正确性。

  sub-concept 2: 运行期 metadata — per-request block map 传递

    对于每个被调度的请求:

      // Producer:
      metadata_out = {
        request_id,
        blocks: [ (block_hash, n_tokens, gpu_offset), ... ],
        kv_cache_spec,         // layout spec (HND or NHD)
      }
      send_metadata(metadata_out)

      // Consumer:
      recv_metadata()  →  metadata_in
      // 据此预留本地 KV cache blocks 并注册接收 offset

  sub-concept 3: Cross-Layer Block Layout (可选优化)

    NixlConnector 支持 cross-layer block 布局 (HND 格式下):[reference:11]

      prefer_cross_layer_blocks: bool

    当开启时，同一 token 的所有 layer 数据连续存放，
    传输时可一次性发送全部 layer，减少 metadata 开销。

    对比:

      逐层 HND:     发送 L 次，L × metadata_overhead
      cross-layer:   发送 1 次，1 × metadata_overhead

  → Q4: 方案完备——但有代价。
        NIXL 选择非阻塞 API 引入的不确定性如何管理？
        producer/consumer 速率失配时内存如何不泄漏？
```

## Q4 → 资源管控、监控与健壮性

```text
Q4 (异步引入的不确定性与资源安全)

  sub-concept 1: 异步 poll 模型

    Worker 在每个 forward batch 的关键路径上统一 poll:
      - start_load_layer():  在推理使用某 block 前调用，
        若对应 receive 未完成则 wait 或 checkpoint
      - start_save_layer():  仅入队发送而不等待完成
      - 发送完成由 Consumer 端确认后通知 Producer 释放 block

    这保证:
      - Consumer 绝不会在数据未到前读取脏 KV
      - Producer 不会过早释放仍在传输中的 block

  sub-concept 2: Block Hold & Release 生命周期

    Producer 侧:

      alloc_block()  →  state: ALLOCATED
      start_save_layer() → state: SENDING  (hold refcount++)
      Consumer ACK   →  state: SENT  (refcount--, candidate for free)

    Consumer 侧:

      recv_metadata() → alloc_block() → state: RESERVED
      start_load_layer() → wait completion → state: LOADED

  sub-concept 3: Metrics & Observability

    NixlConnector 提供 Prometheus metrics 暴露:[reference:12]

      - nixl_transfer_bytes_total        (counter)
      - nixl_transfer_duration_seconds   (histogram)
      - nixl_pending_transfers           (gauge)
      - nixl_transfer_errors_total       (counter)

    通过监控 pending 积压量可实时感知 Producer/Consumer 速率失配。
```
