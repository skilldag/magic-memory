USEEFFECT(7)                   React Core Hooks                    USEEFFECT(7)

NAME
       useEffect —— 在浏览器绘制后异步执行副作用，连接纯渲染与外部世界

SYNOPSIS
       function useEffect(effect: EffectCallback, deps?: DependencyList): void

       type EffectCallback = () => (void | Destructor)
       type Destructor     = () => void
       type DependencyList = readonly unknown[]   // 仅浅比较，若全等即跳过

DESCRIPTION
       组件主体必须是纯函数（无副作用），但应用必然需操作网络、订阅、计时器等。
       useEffect 将此类副作用推迟到浏览器完成布局与绘制之后，不阻塞 UI 更新，
       并通过依赖数组控制执行频率与资源释放，形成“声明式副作用”模型。

   ● 问题零：渲染须纯净，如何安全注入副作用（如数据请求、DOM 操作）而又保持交互响应？
       → 解决：useEffect 异步调度
           副作用函数 effect 不会在 render 阶段运行，而是在 commit 阶段后，
           待浏览器将变更绘制到屏幕之后，才被 React 安排执行。
           调度原理：
               render → 构造 Fiber 树，收集 effect 标记，
               → commit（DOM 变更） → 浏览器 paint
               → 异步执行 flushPassiveEffects（useEffect 回调在此）。
           因此绘制不会被阻塞，用户感知更流畅。

   ● 问题一：每次更新后均运行 effect 会导致性能浪费与无限循环（effect 内 setState）。
       → 暴露缺陷：若不控制重复执行，订阅-取消反复触发，甚至形成渲染风暴。
       → 解决：依赖数组 (Dependency Array)
           提供 deps 参数，React 在每次执行前将依赖项与上次值进行浅比较：
               shouldReinvoke = deps.some((d, i) => !Object.is(d, prevDeps[i]))
           若全部相同，则跳过本次 effect；若不同，则先运行上一次清理，再执行新 effect。
           空数组 [] 等效于“始终不变”，effect 仅在挂载时运行一次，卸载时清理一次。

           隐式契约：effect 内使用的所有组件内响应式值（props、state、
           以及由其衍生的变量）必须出现在 deps 中。
           违反会引入“过时闭包”（见问题三）。

   ● 问题二：部分副作用需要释放资源（取消订阅、清除定时器、打断网络请求），
             否则产生内存泄漏或行为错乱。
       → 解决：清理函数 (Destructor)
           effect 回调可以返回一个无参清理函数。
           生命周期：
               mount：执行 effect，记下 cleanup。
               update (deps 变化)：
                   1. 调用旧 cleanup （使用上次闭包中的变量）。
                   2. 执行新 effect，记下新 cleanup。
               unmount：调用最后一次 cleanup。
           时序公式可表示为：
               effect_n      = fn(scope_n)   // 依赖捕捉 scope_n 的快照
               cleanup_n     = effect_n()    // 若返回函数
               invoke loop: cleanup_{k-1}() → effect_k() → cleanup_k
           此模式确保“获取-释放”严格配对，ResizeObserver、WebSocket 等均受益。

   ● 问题三：若依赖数组声明不全，effect 闭包捕获到的是旧渲染的变量快照，
            形成“过时闭包”（Stale Closure），导致读取到过期状态。
       → 原理：每个渲染周期有独立的 props 和 state，effect 同理。
           若未将某个变量列入 deps，则 React 会认为该 effect 不需依赖该变量，
           即便变量已在新渲染中变化，effect 仍持第一次绑定时的值。
           例如：
               useEffect(() => { console.log(count) }, [])   // 始终打印 0
       → 解决：精准声明依赖 + 工具约束
           a) exhaustive-deps lint 规则：
               eslint-plugin-react-hooks 在编译期校验 deps，所有在 effect
               内读到的作用域变量均应出现在数组中。
           b) 若确需读取最新值但不希望触发 effect，可借助 useRef：
               const latest = useRef(prop); latest.current = prop;
               effect 内读取 latest.current，无依赖变化。
           c) 使用 useCallback/useMemo 稳定函数/对象引用，避免 deps 变化过频。

   ● 问题四：某些副作用需在浏览器绘制之前同步完成，避免用户察觉闪烁或布局跳动。
            （例如测量 DOM 尺寸后立即同步修改）
       → 分析：useEffect 在 paint 之后，不满足同步要求。
       → 解决：useLayoutEffect
           签名与 useEffect 完全一致，但在 DOM 变更后、浏览器绘制前**同步**执行。
           流程对比：
               mutation (DOM 更新) → layout effect 同步运行 → 浏览器 paint
               而 useEffect：paint 之后异步运行。
           代价：layout effect 中的长时间任务会阻塞视觉呈现，须谨慎使用。
           也因此，服务端渲染（无浏览器环境）下使用会抛出警告。

   ● 延伸一：严格模式与重复调用
       React 18+ 严格模式下，开发环境会故意“挂载 → 卸载 → 挂载”组件，
       以暴露未正确清理的副作用。
       这意味着 effect 会“挂载执行 → cleanup → 再次挂载执行”。
       这要求 effect 必须是幂等/可复启的，cleanup 必须彻底。

   ● 延伸二：与外部状态库的集成
       许多状态管理库的订阅 API 本质上就是在 useEffect 中建立订阅并返回 cleanup：
           useEffect(() => {
               const unsubscribe = store.subscribe(handleChange);
               return unsubscribe;
           }, [store, handleChange]);

   ● 延伸三：将副作用声明为“事件”而非“响应”（实验性）
       有提案引入 useEffectEvent，允许在 effect 内读取最新值而不列为依赖，
       解决某些“不想要响应依赖变化，但需最新值”的场景。

SEE ALSO

       exhaustive-deps(3), react(7), reconciliation(7)
